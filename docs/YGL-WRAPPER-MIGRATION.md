# ygl-trees 高级封装：架构约束、接口证据与迁移路线

状态：用户已裁定架构边界，具体分阶段实施路线待确认。产品基线：0.2.0；本机探测对象：已安装的 ygl-trees 0.125.0。没有据此宣称最新版本、完整迁移或全部原生恢复能力已经验证。

## 已确定的边界

用户原话：“底层是对 ygl-trees cli 的高级封装，不可偏离独立实现。”

retouch 是电商修图与动态上下文工程的领域入口。项目、任务、工件、关系、知识、节点状态与索引复用 ygl CLI 及其原生扩展机制。retouch 可以提供业务 schema、参数预检、命令编排、素材处理、ZIP 文件封装、统计视图和宿主交接，但这些功能的事实承载仍在 ygl。

正常运行不能新建另一套项目／任务／关系数据库、全局 catalog.sqlite、全文检索引擎、版本系统或双写 outbox；也不能通过 db sql 私建影子表，将独立实现藏在 ygl 数据库内。CLI 能力不足时，核验其他原生入口，必要时补 ygl CLI／认可的插件扩展，再由 retouch 调用。

图像原始字节、处理结果、ZIP 和临时派生缓存可以是文件；它们的身份、来源、有效版本与业务关系通过 ygl 登记。缓存删除后，应能从原生事实恢复上下文，不依赖另一个业务账本。

## 0.2.0 的偏差和已验证边界

0.2.0 使用独立 ledger.sqlite 保存 Project／Task／Run／Artifact 等实体，ygl 保存计划与证据投影；这一分工不符合最新约束。现有 42 项测试证明该历史实现的业务行为和恢复机制通过，不证明它符合高级封装架构。

需要将现有独立 Store 收敛为只读迁移来源，迁移后从正常运行路径移除。不能在此基础上继续叠加独立的全局目录、标签库或偏好引擎。旧数据先导出、预检与映射，保留历史原文、版本、实际图像、来源和未知请求；不因迁移重做业务操作。

Issue #1 和 #2 按新架构重开复验。原始 Issue 中独立 SQLite 为权威的描述属于旧实现依据，已由最新用户裁决替代；完成标准仍包括完整项目关联、真实进度、ZIP 往返与不重复执行。

## 原生接口探测

可重复入口：

```text
node scripts/probe-ygl-wrapper.mjs --ygl-entry <已安装的-ygl/dist/bundle/bin.cjs>
```

脚本只在项目 tmp 中创建独立 ygl home，调用原生 CLI；不创建 retouch 的 ledger.sqlite，不访问默认业务库，不发出图像请求或独立付费 API 请求。详细 JSON 证据留在本地 `docs/verification/ygl-wrapper-probe.json` 和对应 tmp 运行目录，含实际退出码、解析结果、发行包身份及断言，不参与 Git。

本次结论为 **PASS_WITH_GAPS**：已通过原生核心流程的 9 项结构／关系断言，同时明确保留未满足的契约。

| 能力 | 实际观察 | 封装原则 |
| --- | --- | --- |
| `project new`、`agent brief --project` | 返回真实项目身份、上下文与 next_actions | 原生项目 ID 为依据，不维护独立 Project 真相 |
| `task add --project --node`、`task done` | 任务为原生 kind=task 工件，meta 中保存状态，并自动 tracked-by 挂节点 | 复用任务身份及生命周期，不能另起 Task 表 |
| `produce spec` | 原生 kind=spec、project_id、content、version | spec 进入原生工件索引 |
| `produce design --design-type arch` | 原生 kind=design，meta.design_type=arch | 架构／设计记录走原生 design，不只留散落文件 |
| `node add --tags` 与 `kb add --tags` | 原生标签字段保留中文标签 | 优先使用原生标签，不另建标签库 |
| `rel add/list` | 实际查询到 tracked-by、decided-by、evidenced-by 和真实目标 ID | 关系必须进入原生 rel，不能仅写本地关系 JSON |
| `node index/validate/export` | 索引与验证执行成功、无结构问题 | 依赖、闭包和索引由原生引擎承担 |
| 重复同 key 的 `node add` | 返回 duplicate，保留旧 payload／tags | 不是更新接口；需要核验原生更新或采用明确的版本化 profile |
| 重复 `task add`／`produce spec` | 未满足所需的幂等创建／重放契约，spec 重放产生新工件版本 | 不能把“调用成功”当成幂等；先补原生事务／请求键能力 |
| `db workspace list` | 未得到可验证的工作区清单 JSON | rc0 不证明接口可用；登记和全局查询需要继续核验原生入口 |
| 项目范围 ZIP、身份保真导入、图像执行回执 | 本探针没有验证完整承载契约 | 保留为原生核验／扩展项，不能用旧独立账本替代后宣称完成 |

原生命令的 JSON 形状不一。例如本次 node show 的 payload 为 JSON 字符串，node export 里为结构化对象；task 状态位于 meta。封装按各命令的实测 schema 解析，不使用 stdout 子串或 rc0 推断成功。

## 领域能力映射

| 电商领域概念 | 首选 ygl 承载 | 需要明确的补充契约 |
| --- | --- | --- |
| 业务项目 | 原生 project | 业务对象与原始意图的 profile、收口元数据更新 |
| 目标、需求和版本 | 原生 node.payload、spec 与关系 | 目标版本／保持项／事实角色，实际更新或不可变版本链 |
| 修图步骤与依赖 | 原生 tree/node、link/cond、task --node | 一个领域步骤与真实任务／工件的稳定绑定 |
| design 与 spec | 原生 produce、artifact.version、rel | 精确版本引用、来源与确认状态 |
| 标签、评分、结语、方法论 | 原生 tags、payload、kb、spec/design 及 rel | 版本化 profile 与有效版本选择，不能误用 duplicate 当更新 |
| 原图、模型结果、后处理与交付 | 原生 artifact/source/evidence 或明确的媒体扩展 | 字节身份、实际尺寸、相对文件定位、派生链 |
| 请求、授权、未知结果、审阅 | 原生工件／来源／证据／状态及必要的原生执行扩展 | 原子意图、稳定请求键、重放标识、历史权限隔离 |
| 跨项目引用和动态上下文 | 原生 rel、kb search、agent brief、显式工作区读取 | 角色、来源版本/hash、失联和过期诊断 |
| 全局品味与二次分类 | 对原生标签与反馈查询结果做派生统计 | 逻辑项目去重、样本与分母、方法版本；无独立搜索库 |
| ZIP 交换 | 封装已验证的原生导出／导入与文件打包 | 关系闭包、身份映射、事务提交、恢复与重复导入 |

本表是映射目标，未核验的字段和扩展不能被写成已实现命令。不得把媒体冒充 spec、把图已生成等同 node unlock、把用户未反馈写成零分，或将本地缓存补同步视为事实已落 ygl。

## 唯一写入路径与幂等

正常写入路径为：电商预检 → 原生 CLI／原生扩展命令 → 校验退出码及 JSON 绑定 → 读取原生结果生成视图。工作区、项目和树显式指定，沿用原生身份，不依赖全局最后选择指针。

跨多条 CLI 的流程不能自动视为事务。尤其是“任务已创建但封装进程未收到结果”与“图像请求未知”，需要原生请求键、命令收据或可验证的对账原语。只有观察到首次有效执行意图才可调用宿主一次；重放、原生调用结果不明和索引修复都不能引发第二次出图。

现有发行版不能保证的原子性，先通过原生扩展补齐，不创建 retouch.commands／outbox 来接管权威状态。插件也必须使用 ygl 的数据模型与事务边界，不能另建影子项目／运行库。

## 推荐实施路线

### 第一步：冻结原生 profile 与封装入口

完成实体、ID、版本与关系映射，补齐工作区登记、元数据更新和幂等的实际契约；建立严格 native JSON client 与电商 profile。优先使用现有 CLI，缺口在 ygl 原生接口／插件层解决，隔离验证后再接 retouch。

出口：只用 ygl CLI 就能查询真实项目、任务、spec/design、标签和来源关系；封装的相同请求不会重复建任务。正常 retouch 入口不创建独立业务数据库，不使用 db sql 创建影子系统。尚不能满足的契约具体列出并留为未通过。

### 第二步：迁移现有工作流、ZIP 与恢复

原独立账本只读导出，先生成 dry-run 映射和冲突报告；迁入原生实体、关系与事实后验证，再切换正常读写入口。保留旧包读取适配、原始身份映射和回退材料，不直接改写真实工作区或删除历史。

将图像输入输出、授权、执行意图、unknown 对账、审阅、接受和交付交给已验证的原生承载；沿用素材处理与 ZIP 文件校验能力。源历史授权不能因迁移激活目标执行权限。

出口：在隔离环境重放 #1／#2 的全部业务验收，包括 200→1254→2048 实际来源链、候选待验收、套图只规划、未知请求保持、原生索引重建、幂等 ZIP 和无重复出图；移除缓存后仍能仅从 ygl 接手。验证完成才重新关闭 Issue。

### 第三步：动态上下文工程

基于原生标签、反馈、工件和关系实现项目收口提醒；跨所有登记工作区检索 design/spec，建立可携带的精确引用；通过版本化方法论生成频率、二次分类、交叉及评分视图，封装为当前任务的上下文和专业建议依据。

出口：同一项目的恢复副本不重复计数，失联／冲突不伪装新鲜，建议可追溯到真实原生工件，用户反馈回到 ygl 后能重建视图，过程中不产生第二个业务或索引引擎。详见 [动态上下文规范](DYNAMIC-CONTEXT.md)。
