# [P1] 强制建立项目—目标—任务—产物关联与索引规范，防止业务上下文漂移

> 当前状态：0.2.0 旧实现与 #2 一起通过 42 项测试；用户随后明确底层必须为 ygl-trees CLI 的高级封装，因此本 Issue 重开，待原生承载迁移和复验。原始正文中的独立 SQLite 权威方案已被最新裁决替代；见 [迁移规范](../YGL-WRAPPER-MIGRATION.md)。下文保留原始需求，不能据历史技术通过宣称新架构已完成。

## 问题

真实使用中，系统能够产生图片、提示词、回执和设计文档，但缺少强制的业务项目管理与统一关联索引。文件已经产出，不代表系统能够说明它服务于哪个目标、采用哪个版本的设计、是否经过用户验收，以及下一步该继续什么。

用户明确要求：**项目管理与相关索引关联规范必须成为强制要求，确保任务与目标的上下文一致性。** 仅补充一份建议性文档或要求 Agent 自觉记录，不能关闭本 Issue；需要同时落实领域数据、CLI 校验、技能操作规范与验收检查。

## 真实使用中观察到的断点

2026-11-14 的床头柜修图与变体规划体验中：

1. 导入商品原图并建立高清重绘任务，随后实际完成一次模型重绘与本地放大。
2. 图片、提示词、外部请求回执和后处理记录写入业务工作目录；最终图片也导入了素材库。
3. 图像执行发生在 CLI 正式运行链之外。已有回执虽包含任务 ID，但没有正式 `run_id`，没有纳入统一运行状态。
4. 实测 `task show` 仍返回 `draft`，`active_plan` 与 `active_run` 均为 `null`；`next` 仍返回 `waiting_for_plan`，建议提交计划。该状态不能表达已存在、尚未由用户验收的外部候选。
5. 后续生成了变体设计与七张套图方案，但文档没有稳定的项目、目标、任务、变体版本和产物身份，也没有通过统一索引关联原图、高清重绘图与事实依据。
6. 需求期望输出 2048×2048，模型原生输出实际为 1254×1254，随后本地放大到 2048×2048。分散记录中存在这一事实，但统一产物链无法直接查询。
7. 原始商品信息、同系列产品资料、Agent 提案与 AI 补绘细节并存。缺少结构化来源和确认状态，后续容易将 AI 补绘图当成已确认的产品结构依据。

这些断点造成了任务状态、实际产物和聊天中的进度三者分离。换会话或换 Agent 后，必须人工拼接聊天与目录才能恢复项目意图。

## 当前实现依据

- `src/domain/model.ts`：已有 Task、Plan、Run、Attempt、Asset 等对象；Task 未显式绑定业务 `project_id`、`goal_id` 或目标版本，Asset 也没有项目归属和用途关联模型。
- `src/application/service.ts`：任务状态主要根据当前 plan/run 推导；正式运行链外的产出无法通过已有 task/next 路径完整表达。
- `src/adapters/ygl.ts`：已有按工作区建立的 ygl project、计划树与运行 context；这不等同于完整的用户业务项目、目标及产物管理。
- `docs/ARCHITECTURE.md`：SQLite 是领域账本，ygl 是可重建投影。新增关联和索引应延续这一分工。

## 目标

任意时刻仅给工作区和项目身份，接手者就能读取：用户目标、当前范围、确认过的事实、待确认项、任务状态、有效设计版本、候选与已验收产物、阻塞原因，以及有依据的下一步。

这是一条业务完整性约束。无需用户管理内部 ID，也不新增逐步人工确认；已在当前会话取得的同范围授权应被记录和复用。

## 必须建立的最小领域关联

以下字段与命令名称是设计要求/拟议接口，不代表当前已实现。

| 对象 | 必须记录的内容 |
| --- | --- |
| Project | 稳定 ID、名称、用户原始项目意图、业务对象标识、状态、当前有效上下文入口 |
| Goal | 所属项目、用户原文、执行解释、范围和保持项、验收条件、版本、确认状态及依据 |
| Task | 所属项目、服务的目标及版本、输入引用、预期交付物、依赖、状态、阻塞原因；有明确终止条件 |
| Design / Variant | 所属项目与任务、设计版本、规格与事实来源、假设、确认状态、前后版本关系 |
| Artifact | 稳定 ID、所属项目、产生它的任务、产物类型、用途、版本、相对定位地址、内容 hash 和状态 |
| Execution | 绑定的任务、计划/操作范围、输入、请求身份、实际执行通道、结果与恢复状态 |
| Review / Delivery | 绑定的具体产物版本及 hash、实际审阅/接受依据、交付位置及状态 |

图片与文件可以被多任务复用，通过用途关系表达，不复制或篡改原始对象身份。初始导入的素材允许处于明确可查询的待归属区；在成为执行输入、任务输出或正式交付物前必须完成绑定。

## 强制操作规范

### 1. 项目与目标先于执行

- 业务任务必须绑定明确的项目、目标及其版本；软件仓库、业务工作区和用户业务项目分别建模。
- 启动、接手和切换项目时，先读取系统生成的项目上下文包，核对当前目标、任务、设计版本和下一步。
- 不依赖 cwd、最后一次聊天消息或全局选择指针来推断任务归属；系统可以代填已确定的身份，但必须持久化。
- 当用户从高清重绘转向变体设计时，记录为同项目下的新目标/子任务或明确的范围变更，保留前序工作及其状态。
- 原图、参考图、AI 重绘、候选、定款图和事实依据使用不同用途标记。AI 补绘的结构细节不能自动升级为已确认产品规格。

### 2. 产出时登记关联

- 图片、设计方案、套图分镜、提示词、尺寸规格、检查与交付记录均作为一等产物登记。
- 至少能沿关系追溯：项目 → 目标版本 → 任务 → 产物；生成图片还需追溯运行/外部操作与输入；设计文档不强制伪造图像运行。
- 关系必须具备明确语义，例如 `derived-from`、`reference-for`、`implements`、`reviewed-by`、`supersedes`。统一词汇表和方向，避免随意字符串。
- 图像尺寸变化要保留完整派生链：原图 → 模型原生结果 → 本地放大结果，不把请求尺寸当成实际输出尺寸。
- 文件可存放在不同目录，但目录本身不承担任务归属与验收状态的唯一证明。

### 3. 外部执行同样纳入账本

- 宿主工具、独立图像 CLI 和后处理工具必须遵循同样的任务/输入/请求/结果关联规范。
- 对暂不支持的执行通道，应记录为可查询的外部操作及明确能力缺口；不能通过散落 JSON 冒充正式运行已完成。
- 操作前记录执行意图；操作后登记真实结果与来源。结果未知时保持待对账状态，不因索引缺失重新生成。
- 允许回接已经发生的外部执行事实；补登记不得触发新的付费调用，也不得补造历史授权、审阅或用户接受。

### 4. 索引是可校验的投影

- SQLite 领域账本为项目、目标、任务、产物与关系的单一事实源；索引、摘要文档和 ygl 关系图由领域事实生成。
- 明确项目级、任务级、产物级的检索入口及版本字段，不维护多套互不校验的“最新状态”。
- 领域写入与索引更新采用事务或已有 outbox 等可靠机制；失败时明确显示待同步，禁止默默展示过期索引。
- 索引支持版本校验、重建、悬空关系检查、hash 检查及待归属资产发现；修索引不能重做业务操作。
- 提供稳定引用和工作区相对定位；移位/迁移后可重新定位与校验，不依赖某台机器的绝对路径。

### 5. 上下文变更和收口检查

- 目标、设计、材料事实或输入改变时，创建新版本并标记受影响的下游任务与产物为待复核；不覆盖历史，不无差别重置全部工作。
- 任务完成、用户验收和正式交付分别记录。完成“方案草稿”任务不等于完成套图生成，也不等于用户接受产品设计。
- 会话结束前检查新增产物是否登记、关系是否完整、索引是否同步、未知执行是否待对账，并保存当前阻塞和下一步。
- 普通低风险记录和已有授权内的动作自动推进；此规范不增加重复审批。

## 强制门槛与错误契约

- 正式执行或发布任务产物前，缺少必要的项目/目标/任务绑定应返回结构化错误；在可能产生外部副作用前阻止执行。
- 对输出登记、任务关闭、用户验收和交付使用阶段适用的完整性检查，不让“待归属”素材永久绕过要求。
- 发现关联缺失、目标版本过期、跨项目误引用或索引陈旧时，返回具体受影响对象和修复动作。
- 已发生的外部结果不得丢弃：先持久化为待归属/待回接事实，再修复关联，不能把校验失败解释为允许重试外部生成。
- 保持现有 JSON 信封、退出码、request-id 重放及 revision 冲突契约；新增错误类型应写入 CLI 文档。

## 建议的接手入口

拟议提供 `project brief` 或等价入口，返回：

1. 项目身份、目标原文与当前版本。
2. 已确认事实、来源、假设和待确认项。
3. 任务清单、依赖、当前任务、阻塞与真实执行状态。
4. 有效变体设计、输入素材、参考素材和版本。
5. 产物索引、派生关系、审阅与用户接受状态。
6. 待同步记录、未知执行、索引版本及具体下一步。

## 验收标准

- [ ] 从用户业务项目开始建立目标与任务，任务必须绑定目标版本，已有 workspaces 的迁移方案明确。
- [ ] 不提供聊天历史，仅根据项目入口，另一会话能正确恢复“高清重绘已有候选、尚未验收；变体与套图仅有方案、尚未执行”的真实状态。
- [ ] 设计文档、图片、提示词和来源均进入统一产物索引；任一产物能反查项目、目标、任务、版本和来源，任务也能查询全部关联产物。
- [ ] 原图、参考图、AI 重绘、候选与用户确认定款图可区分，未确认材质或 AI 补绘细节不会自动作为生产事实传播。
- [ ] 200×200 原图 → 1254×1254 模型输出 → 2048×2048 本地结果的派生、实际尺寸和 hash 可一次查询。
- [ ] 外部图像 CLI 结果可以幂等回接；任务状态和 `next` 能表达已登记外部候选/待回接/待验收，而不是仅根据无 plan/run 返回普通等待计划。
- [ ] 原生 API adapter 不可用时如实记录能力缺口，不伪造正式 run、用户授权或验收，也不为补记录重新发图。
- [ ] 缺关联、悬空关系、跨项目误绑定、旧目标版本、索引陈旧和 hash 不符都有可复核的诊断与修复路径。
- [ ] 索引更新中断后能从领域账本恢复；重放登记/修复/投影不产生第二次业务副作用。
- [ ] 目标或设计更新仅使受影响的下游对象待复核，旧版本与历史接受记录仍可查询。
- [ ] 工作区迁移后仍能通过稳定 ID 与相对地址解析产物；不依赖开发机绝对路径。
- [ ] task/brief/doctor/next 等入口对同一业务状态给出一致结论；任务完成、产物接受和正式交付分别判定。
- [ ] SKILL.md、CLI 文档、架构说明与真实 JSON 契约同步，提供一次新会话接手的完整示例。
- [ ] 测试覆盖缺绑定的执行前拦截、外部结果补登记、未知结果恢复、幂等、索引重建与版本失效；不以仅新增说明文件作为完成。

## 范围与实施顺序

本 Issue 聚焦单工作区内的业务项目、目标、任务、产物与关联上下文，不要求先建设完整企业项目管理平台。

跨会话与跨工作区的上下文迁移由 #2 跟进：交换形式固定为 ZIP 压缩包，基于本 Issue 的稳定身份、版本、产物与关系进行导出、校验和导入。

建议依次交付：最小数据模型与迁移 → 产物登记和关系校验 → 上下文与索引入口 → 外部操作回接 → 强制阶段检查与技能规范 → 真实使用回放验收。

本 Issue 提出的是规范与实现需求；本次提报不代表这些能力已经完成，也不修改既有业务事实。
