# 电商修图流 · 实现路线图

日期：2026-11-14。状态：**路线已确认；M1–M2 已实现，验证结果见正式报告。** 用户补充裁决：宿主图像能力优先，独立图像 API 为 fallback。

## 首个可用版本

用户给一张商品原图和修改要求，Agent 将其组织为可审阅计划，经授权后执行“改把手 → 检查 → 换门板材质 → 检查”，最终展示对照图并由用户验收、交付。

需求组按“文字非空且未停用”参与，各组独立保存补充；Agent 可建议合并或拆分步骤，并说明需求覆盖与次序。后一步必须使用前一步通过检查的真实结果。

第一轮交付 M1–M2 的离线可运行版本，并加入默认 host 的任务单／结果回接协议。它验证图像、状态与恢复；真实 AI 修图效果在可用宿主完成实际出图后验收。

## 技术与职责

- 语言与入口：TypeScript / Node，CLI 命令 `retouch`；先使用 CLI 与宿主技能接入现有 Agent。
- 存储：SQLite 保存业务账本与 outbox，内容寻址对象库保存不可变图像字节；源码与客户业务工作区分开。
- ygl：使用已实测 CLI 的独立 home、冻结树和命名 context，校验 JSON 与业务门结果；适配器严格检查输入。
- 图像：Sharp 本地解码、方向规范化、矩形蒙版、合成、检查与对照；host 执行器对接已有宿主工具，offline 用于 demo，独立 API 为后续显式 fallback。
- 工程：建立本项目的包配置、类型检查与测试，所需开发／图像／存储依赖安装在本项目内。保持现有全局 Node 与 ygl 安装。

M2 的离线输出用于验证流程和图像契约，不代表 AI 已按语义修好商品。host 路径核对当前工具和素材范围，其额度由宿主管理；API fallback 另行核对模型、费用和凭证。M4 的查询、幂等与取消能力以实际执行通道为准。

## 第一轮演示

1. 导入一张测试商品图，记录“改把手”和“换材质”，共享“结构与其他部位保持”约束。
2. 查看明确绑定原图、区域、顺序、预期输出和检查项的冻结计划。
3. 使用离线提供商执行两次局部图像处理，展示每步输入、输出与检查报告。
4. 人为中断并恢复运行，重放同一请求键，验证已有结果不被重复执行。
5. 查看最终对照，记录人工接受，将指定图像与清单交付到明确目录。

这是 M1–M2 的验收演示。真实电商修改效果使用 M3–M5 的提供商与业务样本另行验证。

## 迭代纪律

- 每个阶段交付可运行结果与相应测试，展示实际输出，再按出口判断是否进入后续阶段；不靠增加命令数量判断完成。
- 保留原图、旧计划、历史请求和失败候选；计划或素材改变后，重新核对受影响的授权与下游引用。
- 首版聚焦单商品、单提供商与串行图像写入。批量 SKU、多提供商自动路由、TUI／WebUI、分布式执行和自动知识发布放在后续演进图。
- 密钥通过环境变量或宿主受保护凭证设施注入。配置与诊断仅保留非敏感参数和配置状态。
- 当前用户裁决将早期设计中拟议的新 `retouch-cli/` 项目映射为本目录；原始设计正文与历史 ygl ID 保留，当前执行次序以本路线图及后续用户确认记录为准。
