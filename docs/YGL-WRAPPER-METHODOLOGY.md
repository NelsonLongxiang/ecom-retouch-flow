# ygl-trees 高级封装使用方法论

> **初期引导稿 v0.1｜2026-11-20**
>
> 面向希望借助 ygl-trees，把一类业务工作组织成可执行、可接手、可复用能力的人与 Agent。本文讲如何开展工作、如何形成领域封装，不是 SDK 开发计划，也不是逐条命令手册。
>
> 本稿由 EcomRetouchFlow 实践整理，供领域起步与使用时参考；不覆盖项目现行契约，不授予安装、外部执行、生产、合并或发布权限。

## 一、先建立正确认识

**高级封装的核心，是让使用者表达业务意图，由领域能力组织必要的知识、上下文、行动与检查，再以 ygl-trees 的原生记录保持工作的连续性。**

它不是把几条 CLI 命令改成一个短命令，也不是让 Agent 按固定脚本不加判断地执行。

可以用下面的关系理解：

```text
使用者表达目标
    ↓
领域封装：理解问题 → 选取上下文 → 形成方案 → 组织执行 → 检查交付
    ↕
ygl-trees：项目、任务、规范、设计、来源、证据、关系与知识
    ↕
实际工具与结果：宿主能力、文件、外部服务、人工观察和反馈
```

**用户不必熟悉每个底层对象，但工作不能只留在聊天记录里。Agent 可以推理，但关键依据和进度必须可查询。**

高级封装也不一定从代码开始。初期可以先有清晰的领域方法和 Skill，复用既有原生入口；只有需要稳定编排或强制检查时，才增加相应程序。Skill 是使用指引，不是执行引擎或安全沙箱。

### 什么时候值得采用

适合：需要多轮推进、存在前后依赖、结果会被修订、需要复用历史，或者中断后必须继续的工作。

普通问答、一次翻译、无后续依赖的小操作，不必为了使用 ygl-trees 而建立整套模型。已有高级封装能完成任务时先复用，不因客户、日期或批次变化再复制一个产品。

## 二、一条主线：先完成真实工作，再形成可复用能力

建议始终沿这条主线推进：

```text
真实需求 → 明确目标 → 组织依据 → 设计工作路径
→ 在授权内执行 → 复核与交付 → 保留接手现场 → 提炼可复用方法
```

每一步都回答三个问题：

1. **为什么做？**对应哪个目标、问题或需要消除的不确定性。
2. **依据什么？**来自什么记录、版本、来源和实际观察。
3. **怎样才算做到？**由谁按什么条件判断，哪些仍未知。

不要求每次都填大表；但不能在这三个问题没有答案时，用更多工具调用代替思考。

## 三、七步工作法

### 第一步：用业务结果定义任务，不从命令出发

先表达使用者想解决的问题，而不是先说“建几个节点、调用哪些工具”。最少明确：

- 为谁解决什么问题，结果将如何使用。
- 当前已经有什么材料，哪些是事实、参考、假设或未知。
- 需要交付什么，什么条件满足后才可以收口。
- 允许哪些动作、成本和材料使用范围；哪些事情不在本次范围。

**例子：**不要只写“生成七张图”；应写“让购买者看清商品结构、材质和使用方式，交付适用于指定渠道的图组，商品信息不得被误改”。张数与尺寸可以是约束，但不能代替目的。

**本步产出：**简明目标与验收条件，保留用户原文和 Agent 的解释差异。已有项目就接续，不重复登记；关键事实只有用户能提供时再询问，已经给过的先回读。

### 第二步：先接手已有上下文，再决定补什么

开始工作时先查当前项目、既有任务、最新规范、方案、产物和未决问题。采用已有高级入口时，优先用它的 brief/context；必要时再通过原生入口查明依据。

重点区分四类材料：

| 材料 | 使用方法 | 不应做什么 |
|---|---|---|
| 当前对象事实 | 核对对象身份、来源及适用范围 | 把参考对象的特征当当前对象事实 |
| 规范与约束 | 确认当前版本和本步适用条件 | 用旧规范支持新执行 |
| 方案与历史结果 | 参考选项、取舍和失败原因 | 把曾经接受等同本次仍适用 |
| 方法与经验 | 辅助判断，检查与本任务差异 | 把高频偏好当成强制事实 |

**上下文不是越多越好，而是足够支持下一项决定。**需要能说明“为什么选它、对哪一步有用、是否过期或冲突”。检索命中只是候选，不自动等于采纳或允许向外部服务发送。

**本步产出：**当前已知、关键未知、冲突及下一步所需材料。只有会改变当前决定的缺口才优先补证，不无边界调研。

### 第三步：组织工作路径，而不是堆任务清单

从目标倒推必要步骤，写清每一步的输入、产出、前置与判断条件。

- 有依赖才建依赖；不能把所有任务都串成一条线。
- 探索性的内容先允许比较方案，不提前伪装为确定结论。
- 高成本或高风险批量行动，优先用代表性小样检验关键假设；已有明确批量授权和路线的，不额外制造重复审批。
- 依赖关系复杂或确有能力里程碑时使用 tree/node；简单任务用 task 与工件关联即可，不强制每个项目建树。

**本步产出：**可说明因果的计划。示例：先确认商品事实与用途，再形成图组方案，再验证风险样张，之后制作与复核；不是先批量制作，最后补写方案。

### 第四步：把方案变成绑定依据的行动

执行前核对当前动作实际采用的需求、输入、方案、检查标准与授权。关键对象使用已有契约支持的身份和版本绑定；不能仅靠文件名或“最新版”三个字。

**探索可以动态，具体执行要有确定依据。**新反馈可继续进入项目，但不能悄悄改写已执行动作的旧依据。授权撤回等停止条件不因意图已经冻结而失效。

已有领域入口能做的就调用；没有相应能力时，先确认原生入口或已认可插件是否可表达。不能因为 CLI 有缺口，就私建另一套项目、任务或版本账本。

对有外部副作用的行动，必须区分：

```text
计划做什么 ≠ 已登记意图 ≠ 已发送请求 ≠ 已收到结果
≠ 检查通过 ≠ 已被接受 ≠ 已交付
```

这是语义区分，不是要求所有领域使用统一状态枚举。超时或中断不证明未执行；先查询既有请求、回执与结果，不自动重复出图、付款、发信或发布。

**本步产出：**可追溯的实际动作与结果；没有执行或无法确定的，如实保留。

### 第五步：按目标复核，而不是按产物数量判成功

检查至少分清：

1. **技术正确性：**文件可读、对象和来源绑定正确、必要字段齐全。
2. **内容适用性：**是否解决目标问题、违反保持项、出现歧义或遗漏。
3. **业务接受：**有权接受的人是否接受了这份确切结果。
4. **实际交付：**结果是否按约定交付到目标，并保留真实证据。

确定性问题优先机械检查；语义问题需要实际材料和观察。提示词要求“正确”不证明结果正确，模型自述或软件 PASS 也不自动等于用户接受。

失败要保留，并定位具体原因：来源不够、理解错误、方案不合适、工具能力不足，还是判据本身有问题。只改受影响部分，不通过删除失败记录、补造证据或降低标准把结果变绿。

**本步产出：**有依据的结论与必要修订。证据不足保留未知，未观察或未运行不计通过；状态名称按项目真实契约使用。

### 第六步：收口时留下可以继续工作的现场

接手摘要至少能定位：

- 当前目标与有效版本。
- 已完成和未完成的实际工作。
- 当前产物、检查、接受与交付依据。
- 失败、冲突、外部执行未知和在途事项。
- 下一步可做什么、需要什么材料或授权。

摘要应从原生记录和必要原始文件形成，不是另一套独立进度表。必要时更新原生关系、任务状态和健康诊断；不要仅把“做完了”留在聊天里。

任务不做了就按现有入口说明取消或替代理由，不伪装完成。变更结构时维护相应索引与验证；未动结构不机械重建所有索引。

**本步产出：**另一位 Agent 不靠原作者记忆，也能解释已发生、仍未知和允许的下一步。

### 第七步：从反馈中提炼方法，不把每次结果都变成规则

一次任务的全部细节不应原样塞进 Skill。先判断哪些东西在更换实例后仍有用：

| 内容 | 应放在哪里 |
|---|---|
| 当前客户、商品、批次的事实和接受 | 当前业务项目的原生记录 |
| 可复用的判断、反例与来源 | 原生知识及其证据关联 |
| 何时使用、如何决策、最短流程与停止条件 | 领域 Skill 的稳定使用入口 |
| 重复且可确定执行的机械步骤 | 已维护工具或领域命令，不复制临时脚本 |
| 跨领域的身份、事务、版本和收据缺口 | ygl 上游议题与统一 SDK 契约 |

验证经验是否可复用，要换一个没有参与编写的新实例，观察实际决策、产物与成本；不能只读文档后宣称通用。证据暂不足时可以保留候选；无有效增量就不新增规则。

**本步产出：**少量有来源、有适用条件、有反例的稳定方法，而不是越来越长的提示词。

## 四、ygl-trees 在方法中的位置

下面是概念映射，不是要求每个项目创建全部对象。具体类型、字段与命令以当前实际版本和已验收封装为准。

| 工作中的问题 | 原生承载方向 | 使用原则 |
|---|---|---|
| 我们在做哪件事？ | project | 已有业务身份优先，不按会话或日期重复建项目 |
| 接下来具体做什么？ | task | 绑定目标与完成依据，状态反映真实动作 |
| 什么必须满足？ | spec 等规范工件 | 保留原文、版本及作用域，不混入未经确认推测 |
| 为什么选这个方案？ | design 等设计工件 | 保留取舍、依据、未选方案与后果 |
| 判断从哪里来？ | source / evidence / claim | 来源、原文摘录和解释分开，不强迫所有领域事实都塞进 claim |
| 对象之间是什么关系？ | rel | 重要关系要可查询，不能只藏在备注里 |
| 先做什么才可做什么？ | tree / node / 条件 | 有实际依赖再建模；解锁标记不替代业务证明 |
| 下次怎样复用？ | kb / skill | 先有证据和方法，再提升；能创建不等于已加载或有收益 |
| 接手先看什么？ | agent brief / 领域 brief-context | 先读当前项目，再按需展开，工具建议不自动扩大权限 |

### 关联是关键，不是额外装饰

只存对象，没有关系，很容易出现“任务在一边、方案在一边、证据在另一边”。至少要查清：

- 哪个任务在实现哪个目标。
- 哪份方案约束了哪次执行。
- 哪个来源支持哪条判断。
- 哪个结果由哪些输入产生。
- 哪个检查或接受针对哪个确切结果。

关系语义优先复用原生与领域现行词汇，不自行假设所有动词都已支持。关键依赖进入原生结构，文档用于解释，不再维护一份平行关系真相。

## 五、从初期方法到高级封装：逐层增加，而非一次造平台

### 第一层：先能按方法完成一个真实任务

使用已有 ygl 和领域入口，保留目标、依据、结果及下一步。先检查是否真有业务价值，不以文件、命令或节点数量作为进度。

### 第二层：把稳定判断写进使用入口

将适用场景、常见分支、关键反例、停止条件写成领域方法或 Skill。实例参数留在输入中；不要每个客户复制一套能力，也不要让 Skill 承担独立状态存储。

### 第三层：把重复机械工作交给稳定工具

当输入检查、对象查询、关系挂接、结果整理等动作确有重复且可以验证，再复用或增加领域命令。选择工具是为了减少遗漏与不确定性，不只是少打字。

关键约束若必须强制成立，应放在相应执行入口或原生事务中；不能仅靠提示词“必须”。多条命令顺序执行不天然等于一个事务。

### 第四层：用新实例检验，再提炼通用性

更换输入、环境或业务边界，看同一方法是否仍能正确判断。领域知识允许充分表达；身份、版本、关系和事务等基础设施不要重复。

**通用性的证据是不同真实消费者共享同一契约，且保留各自领域意义；不是给函数换一个抽象名字。**只有一个领域运行成功，就只报告该范围。

### 统一 SDK 是底线，不是使用方法的前置阻塞

外部领域入口优先经已核验的 CLI/统一客户端；进程内插件使用受支持的宿主能力。共享同一套身份和业务契约，不建立第二套 SDK、项目账本、版本引擎或检索权威。

统一 SDK 尚未交付时，继续复用已验收入口，不把规划中的接口写成可调用能力；也不自动升级共享安装。验证器继续遵守既有 CLI 执行边界。

## 六、一个贯穿例子：商品图制作

这是方法示意，不是已经执行的业务案例，也不是必须采用的固定图组模板。

**需求：**让购买者了解某商品的结构、材质和使用方式，形成可交付图组，商品信息不能被误改。

| 阶段 | 怎么做 | 留下什么 |
|---|---|---|
| 定义 | 明确渠道、受众、用途、保持项、交付和授权 | 原始需求与当前规范 |
| 接手 | 查原图、规格、已有方案和返图反馈 | 当前事实、参考与未知的区别 |
| 策划 | 将买家问题映射为画面职责，选择风险代表样张 | 方案、取舍和步骤依赖 |
| 执行 | 在已有授权内，绑定实际输入与方案版本调用可用工具 | 执行意图、实际回执与原始结果 |
| 复核 | 看实际图是否表达目标，保持项是否满足 | 指向具体对象与问题的观察，不用张数冒充覆盖 |
| 交付 | 当前检查、接受和文件发布分别确认 | 确切产物、接受与交付依据 |
| 复用 | 提炼哪些画面职责与反例有迁移价值 | 带适用条件的方法，不复制商品事实 |

如果中途要求更换用途：保留旧图和旧接受，明确受影响的方案、检查与任务；不能因为图片仍存在，就继续当成新用途已经完成。

换成研究报告时，同样可以沿“研究问题→来源与证据→判断与报告→复核交付→经验复用”推进。具体产物与判据不同，连续性和依据链相同。

## 七、每次实际使用的最短节奏

### 开始时

读当前项目摘要 → 确认目标与已有进度 → 找到本步相关方法和材料 → 决定最小下一步。

### 进行中

有新事实就更新对应记录；有判断就关联依据；有变化就标出影响；有未知外部执行就先对账。不是每条聊天消息都新建一条业务记录。

### 结束或交接时

核对实际产物、接受和交付范围 → 更新任务与必要关系 → 留下未知和下一步 → 只有可复用增量才沉淀经验。

必要诊断、索引维护和备份使用已授权入口；不为了执行本节而默认安装组件、调用付费模型、建立定时任务或修改宿主。

## 八、判断高级封装是否有效的五个问题

1. 用户是否可以用业务语言表达目标，而不必先学底层命令？
2. Agent 是否真正引用了当前材料，并能解释为什么选择该方案？
3. 产物是否按业务目的复核，而不是仅凭 rc0、文件数或自述成功？
4. 换会话、中断或需求变化后，能否继续而不重复做过的外部动作？
5. 换一个新实例后，稳定方法仍可用，而实例事实没有被错误迁移？

若答案未知，先核实对应案例；不要立刻增加框架、节点或规则。初期优先修复会阻断真实闭环的问题。

### 常见偏差与纠正

| 偏差 | 纠正 |
|---|---|
| 从工具清单开始设计业务 | 先写结果与完成条件，再选最小能力 |
| 每项任务都建一棵树 | 只对真实依赖和能力里程碑建树 |
| 把所有历史复制进上下文 | 只选影响当前决定的材料，保留来源与冲突 |
| 在聊天里完成，在库里仍待办 | 用真实入口更新状态与证据关系 |
| 超时就重试，旧图就复用 | 先对账；复用前核当前适用性 |
| 每次纠偏都新增一条强制规则 | 先判断原因、适用范围与反例，再决定是否沉淀 |
| 封装自己保存真正进度，ygl 只做投影 | 把权威收回原生记录，外层仅组织、验证和派生视图 |
| 等统一 SDK 完成才开始业务方法 | 先用已核验能力跑闭环，缺口上报而不私建底座 |

## 九、可直接使用的一页方法卡

把下面内容填入已有项目/任务或正式设计即可，不强制另建文件。它是工作表，不是 API schema。

```text
业务目标：为谁解决什么问题，结果如何使用？
完成条件：交付什么，由谁按什么标准判断？
已有上下文：当前项目/任务、输入、规范、方案和历史结果在哪里？
关键未知：哪些会改变当前决定，如何取得最小补证？
工作路径：先做什么、依赖什么，每步产出和检查是什么？
本次行动：采用哪些确切输入/版本，现有入口是什么？
执行边界：允许做什么，外发/费用/停止条件是什么？
结果与复核：实际发生了什么，哪些通过、失败或仍未知？
接手下一步：能继续什么，依赖什么，不能重做什么？
复用增量：哪些方法换实例仍成立，证据和反例在哪里？
```

## 十、给 Agent 的引导文本

填写后使用；这段文本帮助组织工作，不替代实际授权或项目规范。

```text
请使用本项目已有的 ygl-trees 高级封装处理以下业务目标：<目标>。
当前范围与授权：<范围、允许动作、禁止动作>。
已有项目、材料和入口：<真实位置或身份>。

先接手当前项目，不重复建对象。区分用户原文、事实、参考、解释与未知。
从交付和完成条件倒推工作路径，再选必要上下文与工具，不先堆命令。
优先复用现有领域 Skill/入口；原生能力不足就明确缺口，不另建权威账本。
具体执行绑定当前输入与依据，外部结果未知先对账，不自动重发。
用实际观察复核业务目的，技术成功、用户接受和交付分别报告。
结束时更新真实状态、证据与下一步；只有有证据的可复用方法才沉淀。
能在既有权限内核验的问题自行查明，只上报必要的业务取舍或新增权限。
```
